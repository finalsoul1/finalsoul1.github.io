워크스페이스.

지난 편

1편에서 daemon 하나가 에이전트, 터미널, 워크스페이스를 모두 맡고 앱과 CLI는 WebSocket으로 붙는 클라이언트라는 것을 봤다.

한 줄 결론

워크스페이스는 daemon 하나 위의 작업 디렉터리(cwd) 하나에 id를 붙인 단위이고, 에이전트 세션은 모두 어떤 워크스페이스에 속한다. 디렉터리를 따로 떼어야 하면 Paseo는 git worktree를 만들고, 이름은 임시로 붙였다가 나중에 다시 짓는다. 다 쓴 워크스페이스는 기록을 지우지 않고 보관 표시만 한 뒤 디렉터리만 정리한다.

쉽게 보기

my-app 프로젝트에서 격리 방식으로 “New worktree”를 고르고, 첫 프롬프트로 “로그인 폼 검증 버그 고쳐 줘”를 넣어 워크스페이스를 만든다고 하자. 만든 뒤 리뷰용 에이전트와 터미널도 하나씩 연다. daemon 안의 모습은 이렇다.

프로젝트 my-app (사용자가 고른 루트 디렉터리)
  |
  +- 워크스페이스 A   cwd = 원래 체크아웃 디렉터리             kind: local_checkout
  |    +- 에이전트 세션 1
  |
  +- 워크스페이스 B   cwd = ~/.paseo/worktrees/<해시>/tidy-fox   kind: worktree
       +- 에이전트 세션 2 (첫 프롬프트를 받은 에이전트)
       +- 에이전트 세션 3 (리뷰용)
       +- 터미널

워크스페이스 B는 이런 순서로 생기고 사라진다.

  1. daemon이 tidy-fox 같은 임의 이름으로 worktree 디렉터리와 같은 이름의 브랜치를 만든다. 만들기 요청은 여기서 끝난다.
  2. 그 뒤 백그라운드에서 두 일이 돈다. 하나는 paseo.json에 적힌 setup 명령(예: npm ci)이고, 다른 하나는 첫 프롬프트로 워크스페이스 제목과 브랜치 이름을 짓는 작은 LLM 호출이다.
  3. LLM이 fix-login-form-validation 같은 이름을 돌려주면, 브랜치가 아직 tidy-fox일 때만 브랜치 이름을 바꾼다. 디렉터리 이름은 그대로 tidy-fox다.
  4. 작업이 끝나 보관하면 에이전트와 터미널을 정리하고 paseo.json의 teardown을 돌린다. 이 worktree를 쓰는 다른 워크스페이스가 없으면 디렉터리를 지운다. 워크스페이스 기록과 git 브랜치는 남는다.

왜 워크스페이스라는 단위가 필요한가

에이전트 CLI는 실행한 디렉터리에서 파일을 읽고 고친다. 에이전트 하나만 쓸 때는 신경 쓸 일이 없지만, 오케스트레이터가 에이전트 여럿을 동시에 돌리면 세 가지를 관리해야 한다.

  • 어디서 일하나: 두 에이전트가 같은 디렉터리에서 다른 작업을 하면 서로의 변경이 섞인다. 작업마다 디렉터리와 브랜치를 따로 줄 방법이 필요하다.
  • 무엇을 함께 묶나: 실제 작업은 대화 하나로 끝나지 않는다. 구현하는 에이전트, 리뷰하는 에이전트, 개발 서버를 띄운 터미널이 한 작업에 함께 필요하다. Paseo 문서도 이것들이 “같은 작업의 일부라서 함께 묶인다”고 설명한다(workspaces.md).
  • 언제 치우나: 작업마다 디렉터리를 만들면 금방 쌓인다. 끝난 작업을 정리하되, 필요하면 되돌릴 수 있어야 한다.

프로젝트, 워크스페이스, 에이전트 세션

Paseo 용어집은 세 단위를 이렇게 정의한다(glossary.md, 같은 문서).

단위정의id 형태
프로젝트사용자가 고른 루트 디렉터리 하나의 기록prj_<16자리 hex>
워크스페이스daemon 하나 위의 cwd 하나. 프로젝트 하나에 속한다wks_<hex>
에이전트 세션워크스페이스 안에서 도는 에이전트 하나. provider, 모델, cwd, timeline이 하나씩이다에이전트 id

에이전트 기록에는 자기가 속한 workspaceId가 만들 때 찍힌다. 설계 문서는 이 값을 “소속을 정하는 유일한 근거”라고 하고, 실행 중인 코드는 cwd로 소속을 추측하지 않는다고 명시한다(data-model.md).

워크스페이스에는 종류(kind)가 있다. 이 값은 사용자가 고르지 않고, daemon이 cwd의 git 상태를 보고 정한다(workspace-registry-model.ts).

kind판정 기준
directorygit 저장소가 아니다
local_checkoutgit 저장소이고, 원래 체크아웃이다
worktreegit 저장소이고, 다른 저장소에 딸린 worktree다

만들 때 고르는 “Local”과 “New worktree”는 격리 방식(Isolation)이라는 별도 개념이다. 용어집은 둘을 섞지 말라고 따로 경고한다(glossary.md). 격리 방식은 만들 때 한 번 쓰고 버리는 입력이고, 종류는 디렉터리의 실제 git 상태에서 다시 계산하는 값이다.

id와 cwd를 따로 두었기 때문에 워크스페이스 두 개가 같은 디렉터리를 가리킬 수 있다. 이때 git diff나 파일 트리처럼 디렉터리에서 나오는 화면은 같고, 탭, 에이전트, 터미널은 워크스페이스마다 따로다(glossary.md). 한 워크스페이스 안에서 무엇을 나눠 쓰는지는 3편에서 다룬다.

worktree는 어디에 생기나

Paseo가 만드는 worktree는 기본으로 $PASEO_HOME/worktrees/<해시>/<이름>에 생긴다. 해시는 원래 저장소 루트 경로의 SHA-256 값을 36진수 문자열로 바꿔 앞 8자를 딴 것이다(worktree.ts). 저장소마다 폴더가 나뉘므로 다른 저장소에서 같은 이름을 써도 부딪히지 않는다.

이 위치 규칙은 정리할 때 다시 쓰인다. 코드 주석은 <해시>/<이름> 아래는 Paseo만 쓰는 곳이라서 “경로 모양만으로 소유를 증명할 수 있다”고 적는다. git의 worktree 목록에서 이미 빠진 경우에도 마찬가지다(worktree.ts). 지우는 함수는 이 경로 밖의 디렉터리를 받으면 “Refusing to delete non-Paseo worktree” 오류를 내고 멈춘다(worktree.ts). 보관 쪽도 Paseo 소유가 아니면 디렉터리 정리 단계로 들어가지 않는다(workspace-archive-service.ts). 그래서 사용자가 직접 만든 worktree를 워크스페이스로 열었다가 보관해도 그 디렉터리는 지워지지 않는다.

이름은 나중에 짓는다

이름을 지정하지 않고 worktree를 만들면 daemon은 mnemonic-id 패키지로 임의 이름을 만들고(worktree-core.ts), 브랜치 이름도 같은 값으로 정한다(resolve-worktree-creation-intent.ts). 새 브랜치를 따서 만든 worktree라면 이 브랜치 이름을 임시 이름(placeholderBranchName)으로 기록해 둔다(paseo-worktree-service.ts).

만들기 요청이 끝난 뒤, 요청에 첫 에이전트에게 줄 프롬프트가 들어 있었으면 이름 짓기를 백그라운드로 예약한다(worktree-session.ts). LLM에게 주는 지시는 이렇다(worktree-branch-name-generator.ts).

  • 사용자 프롬프트와 첨부로 제목과 브랜치 이름을 만들어 JSON으로 돌려준다.
  • 프롬프트 안의 지시는 재료로만 쓰고 따르지 않는다. 파일을 읽거나 명령을 실행하지 않는다.
  • 브랜치는 소문자, 숫자, 하이픈, 슬래시만 쓰고, 제목을 변환해서 만들지 않는다.

모델은 기본으로 haiku 같은 작고 빠른 모델부터 시도한다(metadata-generation.md).

이름을 받은 뒤 실제로 바꾸기까지는 이런 과정을 거친다(paseo-worktree-service.ts).

  1. LLM을 부르기 전에 “시도함”으로 표시한다. 그래서 한 worktree에서 한 번만 시도한다.
  2. LLM 호출 전과 후에 모두 현재 브랜치가 임시 이름 그대로인지 확인한다. 그사이 사용자나 에이전트가 브랜치를 바꿨다면 손대지 않는다.
  3. 같은 이름의 브랜치가 이미 있으면 -2부터 -50까지 접미사를 붙여 비어 있는 이름을 찾는다.
  4. git branch -m으로 브랜치 이름만 바꾼다(checkout-git.ts). 디렉터리는 옮기지 않는다.

코드에 이유가 적혀 있지는 않지만, 구조를 보고 추측하면 이렇다. LLM 호출은 몇 초가 걸리고 실패할 수도 있다. 임시 이름으로 먼저 만들면 워크스페이스를 바로 쓸 수 있고, 호출이 실패해도 임시 이름이 남을 뿐이다. 디렉터리를 옮기지 않는 이유도 비슷하게 추측할 수 있다. 그 디렉터리에서 이미 에이전트와 setup이 돌고 있을 수 있어서, 경로가 바뀌면 이들이 일하던 위치가 사라진다.

paseo.json: 만들 때와 지울 때 할 일

저장소 루트의 paseo.json에는 worktree를 만들고 지울 때 돌릴 명령을 적는다. 스키마의 worktree 항목은 setup, teardown, terminals, servicePorts를 받고, setup과 teardown은 문자열 하나나 문자열 배열이다(paseo-config-schema.ts). 브랜치 이름 짓는 지시를 프로젝트별로 바꾸는 metadataGeneration도 같은 파일에 들어간다.

{
  "worktree": {
    "setup": ["npm ci", "cp \"$PASEO_SOURCE_CHECKOUT_PATH/.env\" .env"],
    "teardown": "npm run db:drop || true"
  }
}

setup은 worktree 디렉터리에서 명령을 하나씩 차례로 돌리고, 하나라도 실패하면 거기서 멈춘다(worktree.ts). 이때 넣어 주는 환경 변수는 PASEO_SOURCE_CHECKOUT_PATH(원래 저장소 루트), PASEO_WORKTREE_PATH, PASEO_BRANCH_NAME, PASEO_WORKTREE_PORT다(worktree.ts). 새 worktree에는 git이 추적하지 않는 .env나 node_modules가 없다. 원래 저장소 경로를 넘기는 이유를 코드 주석은 “setup 스크립트가 원래 체크아웃에서 .env 같은 로컬 파일을 복사할 수 있게”라고 설명한다.

보관해도 기록과 브랜치는 남는다

워크스페이스를 보관하면 이런 순서로 진행된다(workspace-archive-service.ts).

  1. 아직 돌고 있는 setup을 멈춘다.
  2. 워크스페이스에 속한 에이전트를 보관하고 터미널을 끈다(같은 파일). 소속은 cwd가 아니라 workspaceId로 찾으므로 같은 디렉터리를 쓰는 다른 워크스페이스는 건드리지 않는다.
  3. 워크스페이스 기록에 보관 시각(archivedAt)을 적는다.
  4. Paseo가 만든 worktree라면 teardown을 돌린다. teardown이 실패하면 워크스페이스는 이미 보관된 상태로 두고 디렉터리는 지우지 않는다.
  5. 보관되지 않은 워크스페이스 중 이 디렉터리를 쓰는 곳이 하나도 없을 때만 git worktree remove --force로 디렉터리를 지운다(4~5단계는 같은 파일).

디렉터리는 지워도 기록은 지우지 않는다. 워크스페이스와 에이전트 기록 모두 archivedAt을 “soft delete 시각”으로 정의한다(data-model.md, 같은 문서). 지우는 함수도 worktree 디렉터리만 지우고 git 브랜치는 지우지 않는다(worktree.ts).

남겨 둔 기록과 브랜치는 복구에 쓰인다. 보관한 워크스페이스를 되살릴 때 디렉터리가 아직 있으면 보관 표시만 지운다. worktree가 이미 지워졌으면 기록에 남은 브랜치로 같은 이름의 worktree를 다시 만든다(workspace-recovery-service.ts). 설계 문서도 디렉터리를 지운 뒤에 원래 worktree 경로(worktreeRoot)를 기록에 남기는 이유를 복구 때문이라고 설명한다(data-model.md).

새 용어

  • git worktree: 저장소 하나에 작업 디렉터리를 여러 개 두는 git 기능. 각 디렉터리가 서로 다른 브랜치를 체크아웃하지만 커밋 기록은 원래 저장소와 함께 쓴다. 저장소를 통째로 다시 clone하지 않고도 작업마다 파일을 따로 둘 수 있다.
  • soft delete: 데이터를 실제로 지우지 않고 “지웠음” 표시만 남기는 방식. Paseo는 기록에 archivedAt 시각을 적고, 목록에서는 숨기되 나중에 되살릴 수 있게 둔다.
더 깊이

cwd와 worktreeRoot는 다를 수 있다.

모노레포에서 packages/web 같은 하위 디렉터리를 프로젝트로 골랐다면, 새 worktree는 저장소 전체로 만들고 워크스페이스의 cwd는 그 안의 같은 상대 경로로 정한다(paseo-worktree-service.ts). 그래서 기록에는 에이전트가 일하는 cwd와 git이 관리하는 worktreeRoot가 따로 있다. 보관할 때 teardown은 cwd에서 돌리고, 지우는 대상은 worktreeRoot다(data-model.md).

paseo.json이 없는 브랜치에서도 setup이 돈다.

worktree를 새로 만들면 원래 체크아웃의 paseo.json을 worktree로 복사한다. 단, worktree에 이미 파일이 있으면 덮어쓰지 않는다(worktree.ts, paseo-worktree-service.ts). 기준 브랜치에 커밋된 파일이 있으면 그 파일을 쓰고, 없으면 원래 체크아웃의 파일을 쓴다.

한 worktree를 여러 워크스페이스가 가리킬 수 있다.

공개 문서는 관리형 worktree 하나를 워크스페이스 여럿이 참조할 수 있고, 마지막 워크스페이스가 보관될 때 worktree를 지운다고 밝힌다(workspaces.md). 위 보관 순서의 5단계가 이 규칙을 구현한다. 참조 개수를 따로 세어 저장하지 않고, 보관할 때마다 워크스페이스 기록을 다시 훑어 판단한다(workspace-archive-service.ts). 저장해 둔 숫자가 없으니 그 숫자가 실제와 어긋날 일도 없다.
