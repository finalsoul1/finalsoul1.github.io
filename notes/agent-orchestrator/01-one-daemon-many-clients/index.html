NOTES / 01 / 2026.10.29

daemon 하나와 클라이언트 여럿.

한 줄 결론

에이전트 오케스트레이터의 중심은 화면이 아니라 내 컴퓨터에서 계속 도는 프로세스 하나다. Paseo에서는 daemon이 에이전트, 터미널, 워크스페이스를 모두 맡고, 데스크톱 앱, 모바일 앱, CLI는 WebSocket으로 daemon에 붙어 상태를 보여 주고 명령을 전하는 클라이언트다.

쉽게 보기

맥에서 Claude Code 에이전트에게 일을 맡겨 두고 나왔다고 하자. 지하철에서 휴대폰으로 진행 상황을 보다가, 에이전트가 파일을 지워도 되는지 묻길래 승인 버튼을 누른다. 이때 각 부분이 맡는 일은 이렇다.

[휴대폰 앱]        [데스크톱 앱]        [CLI]
     |                  |                 |
     |  WebSocket (daemon에 직접, 또는 relay를 거쳐)
     +------------------+-----------------+
                        |
                 [daemon, 내 맥에서 실행]
                   - 에이전트 세션: Claude Code, Codex, ...
                   - 터미널
                   - 워크스페이스(작업 디렉터리와 git 브랜치)
                   - 에이전트별 진행 기록(timeline)

휴대폰에서 승인 버튼을 누르면 이런 순서로 전달된다.

  1. 에이전트가 권한이 필요한 도구를 쓰려고 하면 daemon이 그 요청을 받아 둔다.
  2. daemon은 이 요청을 그 에이전트를 보고 있는 모든 클라이언트에 보낸다. 휴대폰과 데스크톱에 같은 요청이 뜬다.
  3. 휴대폰에서 승인하면 그 결정이 daemon으로 가고, daemon이 에이전트에 전달한다.

Paseo 설계 문서는 이 흐름을 “agent -> server -> client -> user decision -> server -> agent”로 적는다(architecture.md). 클라이언트는 에이전트와 직접 이야기하지 않는다. 늘 daemon을 거친다.

이 구조를 알면 평소에 보던 현상 몇 가지가 설명된다.

  • 휴대폰 앱을 닫아도 에이전트는 계속 일한다. 에이전트를 실행하는 것은 daemon이고, 앱은 화면일 뿐이다.
  • 휴대폰과 데스크톱이 같은 대화를 보여 준다. 상태는 daemon 한 곳에만 있고, 클라이언트는 그 상태를 구독해서 그린다.
  • 코드는 내 컴퓨터에 남는다. 파일을 읽고 고치고 명령을 실행하는 일은 모두 daemon이 도는 컴퓨터에서 일어난다. 설계 문서도 첫 문단에서 “Your code never leaves your machine. Paseo is local-first.”라고 적는다(architecture.md).

왜 daemon이 따로 있어야 하나

에이전트 CLI 하나만 쓸 때는 터미널 창이 곧 에이전트다. 창을 닫으면 에이전트도 끝난다. 오케스트레이터는 이 관계를 끊어야 한다. 에이전트 여러 개를 동시에 돌리고, 그 에이전트들을 여러 기기에서 보고, 기기가 꺼졌다 켜져도 작업이 이어져야 하기 때문이다.

그러려면 세 가지가 화면과 떨어진 곳에 있어야 한다.

  • 에이전트 프로세스: 화면이 사라져도 살아 있어야 한다.
  • 진행 기록: 나중에 붙은 기기도 지금까지의 대화를 받아 그릴 수 있어야 한다.
  • 작업 공간: 에이전트가 고치는 디렉터리와 브랜치를 누군가 만들고 정리해야 한다.

Paseo는 이 셋을 daemon(packages/server) 한 프로세스에 모았다. daemon은 기본으로 127.0.0.1:6767에서 WebSocket 연결을 받는다(architecture.md). 데스크톱 앱은 daemon을 직접 띄워 관리할 수도 있지만, 띄운 뒤에는 휴대폰과 똑같이 WebSocket 클라이언트로 붙는다(architecture.md).

클라이언트가 daemon에 붙는 방법

클라이언트가 같은 daemon에 붙는 방법은 여러 가지다. 앱 코드는 연결 하나를 아래 여섯 종류 중 하나로 표현한다(host-runtime.ts).

종류언제 쓰나
directTcpdaemon 주소로 바로 붙을 때. 같은 컴퓨터면 127.0.0.1:6767, 다른 기기면 Tailscale 같은 사설망 주소
directSocket, directPipe같은 컴퓨터 안에서 네트워크 포트 대신 OS의 프로세스 간 통신 파일로 붙을 때(macOS와 Linux는 socket, Windows는 pipe)
remoteSsh데스크톱이나 CLI가 SSH 터널로 원격 서버의 daemon에 붙을 때
relay휴대폰처럼 밖에 있는 기기가 중계 서버를 거쳐 붙을 때
routed다른 daemon에 등록해 둔 호스트를 그 daemon을 거쳐 쓸 때

어떤 길로 붙든 그 위에서 오가는 메시지는 같다. 그래서 휴대폰의 연결이 relay에서 직접 연결로 바뀌어도 화면은 그대로 이어진다. 연결을 어떻게 고르고 바꾸는지는 6편, relay를 거칠 때 내용을 어떻게 지키는지는 7편에서 다룬다.

연재 지도

위 그림의 각 부분을 한 편씩 다룬다.

편그림에서 다루는 부분질문
2편daemon 안의 워크스페이스워크스페이스는 무엇이고 어떻게 생기고 사라지나
3편워크스페이스 안의 에이전트 세션들한 워크스페이스의 세션끼리 무엇을 공유하나
4편daemon과 에이전트 CLI 사이서로 다른 에이전트를 어떻게 하나처럼 다루나
5편클라이언트 화면터미널, 파일, diff를 여러 기기에 어떻게 그리나
6편클라이언트와 daemon 사이 연결연결이 끊겼다 붙어도 어떻게 화면을 맞추나

새 용어

  • daemon: 사용자가 직접 보지 않는 곳에서 계속 실행되며 요청을 기다리는 프로세스. Paseo에서는 paseo daemon start나 데스크톱 앱이 이 프로세스를 띄우고, 에이전트는 이 프로세스가 실행한다.
  • WebSocket: 연결을 한 번 맺은 뒤 서버와 클라이언트가 서로 아무 때나 메시지를 보낼 수 있는 통신 방식. 일반 HTTP 요청은 클라이언트가 물어야 서버가 답하지만, WebSocket에서는 에이전트가 새 글을 쓰는 순간 서버가 먼저 클라이언트에 보낼 수 있다.
더 깊이

daemon의 상태는 파일로 남는다.

$PASEO_HOME(기본값 ~/.paseo) 아래에서 설계 문서가 꼽는 주요 파일은 이렇다(architecture.md).

$PASEO_HOME/
  agents/{cwd-with-dashes}/{agent-id}.json   에이전트 기록
  projects/projects.json                      프로젝트 목록
  projects/workspaces.json                    워크스페이스 목록
  schedules/                                  예약 실행 정의와 실행 기록
  config.json                                 daemon 설정
  daemon-keypair.json                         relay 암호화에 쓰는 daemon 키
  paseo.pid                                   실행 중인 daemon의 프로세스와 주소
  daemon.log                                  daemon 로그

daemon을 다시 시작해도 에이전트 목록과 워크스페이스가 남아 있는 이유가 이것이다. 에이전트 기록 파일이 작업 디렉터리 경로별 폴더에 들어간다는 점은 2편의 워크스페이스 이야기와 이어진다.

데스크톱 앱은 웹 앱을 감싼 것이다.

모바일 앱과 웹 앱은 Expo로 만든 한 코드베이스(packages/app)에서 나온다. 웹 빌드 명령은 expo export --platform web이고(package.json), 데스크톱 앱은 Electron 안에서 이 결과물(app-dist)을 불러온다(main.ts). 그래서 데스크톱과 휴대폰의 화면 구성이 거의 같다. 한 코드로 여러 기기를 그리는 방식은 5편에서 다룬다.
