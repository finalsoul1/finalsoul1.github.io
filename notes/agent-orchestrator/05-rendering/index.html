터미널, 파일, diff를 여러 기기에 그리기.

지난 편

4편에서 daemon이 서로 다른 에이전트 CLI를 구조화된 프로토콜로 연결하고, 그 출력을 하나의 진행 기록(timeline) 형식으로 맞추는 방식을 봤다. 이번 편은 반대쪽 끝, 클라이언트가 그 결과를 화면에 그리는 방식을 본다.

한 줄 결론

Paseo는 화면 코드 하나(Expo)로 iOS, Android, 웹, 데스크톱을 만들고, 플랫폼마다 크게 다른 부분만 파일을 나눠 따로 구현한다. 터미널 해석과 diff 색칠은 daemon이 맡는다. 터미널의 현재 화면은 daemon이 따로 띄운 터미널 worker 프로세스 안의 터미널 에뮬레이터가 들고 있고, diff 색칠은 daemon이 파일 전체를 읽어 끝낸 뒤 토큰으로 보낸다. 클라이언트는 받은 것을 자기 화면에 그린다.

쉽게 보기

데스크톱에서 워크스페이스 터미널에 npm run dev를 띄워 두고 나왔다고 하자. 휴대폰에서 그 터미널 탭을 열면 이미 쌓인 서버 로그가 바로 보이고, 새 로그가 이어서 올라온다. 휴대폰은 터미널이 시작될 때 연결돼 있지 않았는데도 지금 화면을 안다.

daemon은 터미널을 별도 worker 프로세스에서 돌린다(worker-terminal-manager.ts). 이 worker는 터미널 출력을 클라이언트에 보내기만 하지 않는다. 화면 없이 상태만 계산하는 터미널 에뮬레이터(headless xterm)에도 같은 출력을 넣어, 아무도 보고 있지 않을 때도 현재 화면을 유지한다. 나중에 붙은 휴대폰은 이 상태를 먼저 받고, 그 뒤 출력을 이어받는다.

왜 오케스트레이터가 화면 그리기를 고민해야 하나

에이전트 CLI 하나만 쓸 때는 터미널 앱이 화면을 다 그려 준다. 오케스트레이터는 사정이 다르다.

  • 같은 터미널과 diff를 여러 기기가 동시에 본다. 늦게 붙은 기기도 지금 상태를 바로 그려야 한다.
  • 기기마다 그리는 기술이 다르다. 브라우저에는 DOM이 있고, 휴대폰 앱에는 DOM이 없다.
  • 휴대폰은 CPU와 배터리, 네트워크가 데스크톱보다 약하다.

그래서 두 가지를 정해야 한다. 화면 코드를 기기마다 따로 짤 것인가, 그리고 터미널 제어 문자 해석이나 문법 색칠 같은 무거운 일을 어디서 할 것인가.

화면 코드는 하나, 다른 부분만 파일을 나눈다

1편에서 데스크톱 앱이 Expo 웹 빌드를 Electron으로 감싼 것이라고 했다(architecture.md).

코드가 하나여도 플랫폼마다 구현이 크게 다른 부분은 있다. Paseo는 이런 부분을 if (isWeb) 분기 대신 파일 이름으로 나눈다. terminal-emulator.tsx와 terminal-emulator.native.tsx를 함께 두면 Expo의 번들러 Metro가 빌드할 때 플랫폼에 맞는 파일을 고르고, 쓰지 않는 쪽 코드는 번들에 넣지 않는다(CLAUDE.md). 데스크톱은 Metro에게는 웹 플랫폼이지만, 빌드 때 PASEO_WEB_PLATFORM=electron을 주면 .electron.tsx 파일을 먼저 찾는다. 그래서 Electron에서만 쓸 수 있는 기능은 이 이름의 파일에 따로 구현한다(CLAUDE.md, metro.config.cjs).

이번 편의 세 화면은 이렇게 나뉜다.

터미널: 현재 화면은 daemon이 들고 있다

daemon의 터미널 코드는 PTY를 만드는 node-pty와 화면 없는 xterm인 @xterm/headless를 함께 불러온다(terminal.ts). 터미널을 만들 때 headless xterm을 하나 만들고(스크롤백 1000줄), PTY 출력이 나올 때마다 이 xterm에도 쓴다(terminal.ts, terminal.ts). 출력이 클라이언트까지 가는 전체 경로는 성능 문서에 정리돼 있다(terminal-performance.md).

클라이언트가 터미널을 구독하면 daemon은 headless xterm의 현재 상태를 ANSI 텍스트(색과 커서 위치를 담은 터미널 제어 문자열)로 다시 써서 한 번에 보낸다. 앱은 보이는 화면 위로 스크롤백 200줄까지 요청한다(terminal-restore.ts, terminal-restore-options.ts). 클라이언트는 이 restore 데이터를 일반 출력과 똑같이 자기 에뮬레이터에 넣는다(daemon-client.ts). 그 뒤에는 restore 시점 이후의 출력만 이어서 보낸다(terminal-session-controller.ts).

터미널 데이터는 JSON으로 감싸지 않는다. WebSocket 바이너리 메시지 하나는 종류 1바이트와 터미널 번호 1바이트 뒤에 출력 바이트를 그대로 붙인 모양이다(terminal.ts, terminal.ts). 출력이 몰리면 5ms 동안 모아 한 번에 보낸다(terminal-output-coalescer.ts). 다만 한동안 조용하던 터미널의 첫 출력은 기다리지 않고 바로 보낸다. 키 입력 에코가 5ms씩 늦지 않게 하려는 것이다(terminal-performance.md).

휴대폰 앱은 WebView로 웹 화면을 띄우지 않는다. 앱 안에서도 @xterm/headless로 바이트를 해석하고(headless-terminal-state.ts), 해석된 화면을 같은 스타일 글자끼리 묶어 React Native의 View와 Text로 그린다(terminal-grid-view.native.tsx). 해석은 웹과 같은 xterm.js 계열 코드가 하고, 그리는 부분만 네이티브 뷰로 바꾼 셈이다.

파일과 diff: 색칠은 누가 하나

파일 보기는 플랫폼에 따라 기능이 다르다. 웹과 데스크톱은 1 MiB 이하 파일을 CodeMirror 편집기로 열어 고칠 수 있고, 휴대폰은 모든 파일을 읽기 전용으로 보여 준다(panel.tsx). 문법 색칠을 하는 크기 한도도 휴대폰이 더 작다. 웹은 10 MiB, 휴대폰은 1 MiB까지 색칠하고, 그보다 크면 색 없이 보여 준다(presentation.ts). 파일 보기의 색칠은 앱이 한다. 한 번에 12ms까지만 색칠하고 나머지 시간은 입력 처리와 화면 그리기에 남겨, 큰 파일에서도 화면이 멈추지 않게 한다(source-lines.ts).

git diff는 daemon이 색칠까지 끝내서 보낸다. 이때 diff에 실린 줄만 보지 않고 파일 전체를 본다. diff 줄만으로는 문법을 정확히 알 수 없기 때문이다.

diff에 실린 부분만 보면              파일 전체를 보면

@@ -40,3 +40,3 @@                    38  /*
   if (cached) {                     39   * 예전 구현:
-    return value;                   40   if (cached) {
+    return value ?? fallback;       41      return value ?? fallback;
   }                                 42   }
                                     43   */
-> 코드처럼 색칠한다                -> 주석이므로 주석 색으로 칠한다

daemon은 바뀌기 전 파일과 바뀐 뒤 파일을 통째로 읽어 각각 색칠한 다음, diff의 각 줄에 해당 줄 번호의 토큰을 붙인다. 코드 주석도 “실제 파일 내용을 쓰면 파서가 더 많은 맥락을 얻는다”고 적는다(diff-highlighter.ts, diff-highlighter.ts). 휴대폰이 같은 일을 하려면 diff 외에 두 버전의 파일 전체를 받아야 하므로, 파일이 이미 디스크에 있는 daemon에서 하면 비용이 적게 든다. 이 마지막 판단은 코드 구조를 보고 한 추측이다.

보내는 토큰은 { text, style } 모양이고, style은 색 값이 아니라 keyword, comment 같은 역할 이름이다(types.ts, messages.ts). 어떤 색으로 칠할지는 클라이언트가 자기 테마로 정한다. daemon이 색칠하는 크기와 시간에도 한도가 있다. 768KB를 넘는 파일은 통째로 색칠하지 않고, 색칠하는 동안 4ms마다 이벤트 루프에 차례를 넘긴다(budgeted-highlighter.ts). 터미널 출력과 에이전트 스트림도 daemon의 같은 이벤트 루프에서 처리되므로, 색칠이 그 일을 막으면 안 된다(terminal-performance.md).

토큰을 받은 뒤 diff 화면을 배치하는 모델은 플랫폼끼리 같고, 그리는 부분만 다르다. 웹은 <canvas>의 Canvas 2D API로, 휴대폰은 Skia(React Native용 2D 그래픽 라이브러리)로 그린다(paint.web.ts, paint.native.ts).

눈여겨볼 설계 선택

터미널 크기는 마지막으로 만진 클라이언트가 정한다. PTY의 크기(행과 열)는 하나뿐인데, 데스크톱 창과 휴대폰 화면의 폭은 다르다. Paseo는 사용자가 터미널을 누르거나 포커스하거나 창 크기를 실제로 바꾼 클라이언트만 크기를 요청(claim)할 수 있게 한다. 붙기만 하거나 보고만 있는 클라이언트는 크기를 바꾸지 않는다(architecture.md). daemon은 마지막 claim의 주인을 기억하고, 다른 연결이 보낸 update는 무시한다(terminal-size-ownership.ts). 그래서 책상 위에 켜 둔 휴대폰이 데스크톱 터미널을 좁히는 일이 없다.

클라이언트의 xterm은 그리기만 한다. nvim 같은 프로그램은 실행 중에 터미널에게 “커서가 어디 있나”, “어떤 기능을 지원하나”를 묻는다. 이 질문에는 daemon의 headless xterm만 답하고(terminal.ts), 브라우저의 xterm은 같은 질문을 받아도 답하지 않게 막아 둔다. 코드 주석이 밝힌 이유는 이렇다. daemon은 PTY와 프로세스 하나만 사이에 두고 있어서, 질문한 프로그램이 끝나기 전에 답이 도착한다. 브라우저가 답하면 그 답은 WebSocket을 거쳐 돌아와야 해서 늦게 도착할 수 있다(terminal-emulator-runtime.ts). 클라이언트가 여럿 붙어 있어도 답은 한 번만 나간다.

색칠 엔진은 하나다. daemon의 diff 색칠, 앱의 파일 보기, 웹 편집기 CodeMirror의 색 규칙이 모두 @getpaseo/highlight 패키지에서 나온다(index.ts). 이 패키지는 CodeMirror가 쓰는 파서 Lezer 위에 만들어져 있다(highlighter.ts). 엔진이 하나이므로 같은 코드는 diff, 파일 보기, 편집기 어디서든 같은 역할 이름으로 나뉜다.

새 용어

  • 터미널 에뮬레이터: 프로그램이 내보낸 바이트(글자와 제어 문자)를 해석해 몇 행 몇 열에 어떤 글자가 어떤 색으로 있는지, 커서가 어디 있는지를 계산하는 프로그램. 화면에 그리는 부분까지 포함하면 xterm.js, 계산만 하면 headless xterm이다.
  • 하이라이팅 토큰: 코드 한 줄을 문법 역할이 같은 조각으로 나눈 것. Paseo에서는 { text: "return", style: "keyword" }처럼 글자와 역할 이름의 쌍이고, 색은 클라이언트의 테마가 정한다.
더 깊이

웹용 터미널 파일 첫 줄의 "use dom".

terminal-emulator.tsx는 "use dom"으로 시작한다(terminal-emulator.tsx). Expo 문서에 따르면 이 표시가 붙은 컴포넌트는 웹에서는 그냥 DOM으로 그려지고, 네이티브에서는 WebView 안에서 돈다(Expo DOM components). Paseo는 같은 자리에 terminal-emulator.native.tsx를 두어 네이티브에서는 이 경로를 쓰지 않는다. 네이티브 쪽은 연결된 daemon이 입력 모드 복원을 지원하지 않으면 터미널 대신 “호스트를 업데이트하라”는 안내를 띄운다(terminal-emulator.native.tsx).

restore 이전의 방식.

바이너리 메시지 종류는 출력, 입력, 크기 변경, snapshot, restore 다섯 가지다(terminal.ts). 설계 문서는 앞의 네 가지만 적고 있어 코드보다 조금 늦다(architecture.md). snapshot은 화면을 칸 단위 JSON(칸마다 글자, 색, 굵기 등을 담은 객체)으로 보내는 예전 방식이고, restore 옵션을 보내지 않는 오래된 클라이언트에게만 쓴다(terminal-session-controller.ts). restore는 같은 상태를 ANSI 텍스트로 바꿔 보내므로 클라이언트가 출력과 같은 경로로 처리할 수 있다. 칸 단위 JSON이 큰 출력에서 얼마나 무거웠는지는 성능 문서에 남아 있다(terminal-performance.md). 끊긴 클라이언트가 다시 따라잡는 과정은 6편에서 다룬다.

웹 터미널은 WebGL로 그린다.

브라우저의 xterm.js는 WebGL 렌더러 addon을 불러 GPU로 그린다. 불러오다 실패하거나 GPU 컨텍스트를 잃으면 이 addon을 내리고 xterm.js 기본 렌더러로 돌아간다(terminal-emulator-runtime.ts).

채팅 안의 diff는 앱이 색칠한다.

에이전트가 파일을 고친 도구 호출을 채팅에서 펼치면 나오는 diff는 daemon이 아니라 앱이 색칠한다. diff 줄로 바뀌기 전과 뒤의 문서를 다시 만들고, 각각을 통째로 색칠해 줄마다 토큰을 붙인다(diff-highlight.ts). 추측이지만, git diff와 달리 파일을 읽지 않고 에이전트 스트림에 실린 내용만으로 하므로 앱에서 해도 부담이 작다고 판단한 듯하다.
