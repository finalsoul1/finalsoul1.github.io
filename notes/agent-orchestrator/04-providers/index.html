서로 다른 에이전트를 하나처럼 다루기.

지난 편

3편에서 한 워크스페이스의 에이전트 세션들이 파일은 함께 쓰지만 대화는 나누지 않는다는 것을 봤다.

한 줄 결론

Paseo는 에이전트 CLI의 터미널 화면을 읽지 않는다. provider마다 그 CLI가 제공하는 구조화된 연결 방식(Claude Agent SDK, codex app-server의 JSON-RPC, ACP 등)으로 붙고, 그 차이를 AgentClient와 AgentSession이라는 공통 인터페이스 뒤에 숨긴다. 그래서 daemon과 앱은 어떤 에이전트든 같은 형식의 진행 기록과 같은 권한 요청으로 다룬다.

쉽게 보기

같은 워크스페이스에서 Claude Code 에이전트와 Codex 에이전트를 하나씩 돌린다고 하자. 둘 다 rm -rf build를 실행하려 하고, 둘 다 실행해도 되는지 묻는다. 휴대폰에는 두 요청이 같은 모양의 카드로 뜬다. 그 아래에서는 이런 일이 벌어진다.

flowchart BT
  cproc["claude 프로세스"] --> sdk["Claude Agent SDK<br/>canUseTool 콜백"] --> cad["Claude 어댑터"]
  xproc["codex 프로세스"] --> rpc["codex app-server<br/>JSON-RPC 승인 요청"] --> xad["Codex 어댑터"]
  cad & xad --> daemon["daemon (AgentManager)<br/>공통 형식:<br/>permission_requested<br/>{ name, kind,<br/>input, detail }"]
  daemon --> app["앱: 같은 모양의 권한 카드 두 장"]

두 CLI가 권한을 묻는 방식은 전혀 다르다. Claude는 SDK가 Paseo의 함수(canUseTool)를 호출하고, Codex는 표준 출력으로 승인 요청 메시지(item/commandExecution/requestApproval)를 보낸다. 어댑터는 이 둘을 같은 permission_requested 이벤트로 바꿔 daemon에 넘긴다. daemon과 앱은 어느 CLI에서 온 요청인지 몰라도 된다.

Claude Code를 Paseo의 터미널 탭에서 claude 명령으로 직접 실행할 수도 있다. 기본 terminal profile 목록에 claude, codex, opencode, pi가 들어 있다(terminal-profiles.ts). 이때 Paseo가 받는 것은 터미널에 찍히는 글자뿐이다. 권한 요청도 화면 속 글자이므로 앱의 권한 카드로 뜨지 않는다. 에이전트 탭에서만 권한 카드가 뜨는 것은 어댑터가 CLI와 화면 대신 프로그램용 연결로 붙어 있어서다.

왜 화면 대신 프로토콜로 붙나

에이전트 CLI는 사람이 터미널에서 쓰도록 만들어졌다. 오케스트레이터가 이것을 여러 개 띄워 관리하는 가장 쉬운 방법은 터미널을 하나씩 열어 주고 그 화면을 보여 주는 것이다. 이 방식으로는 오케스트레이터가 할 수 있는 일이 화면 전달에 머문다.

  • 지금 에이전트가 일하는 중인지, 끝났는지, 내 답을 기다리는지 알려면 화면 글자를 해석해야 한다.
  • 권한 요청을 휴대폰 알림이나 버튼으로 바꾸려면, 화면에서 질문을 찾아내고 키 입력을 흉내 내 답해야 한다.
  • 도구 호출을 “명령 실행”, “파일 수정”처럼 종류별로 보여 주려면 CLI마다 다른 출력 모양을 알아야 하고, CLI가 화면 구성을 바꾸면 깨진다.

Paseo 문서가 이 이유를 따로 적어 두지는 않았다. 위 목록은 터미널 탭과 에이전트 탭의 차이에서 끌어낸 설명이다. 코드에서 확인되는 사실은, 에이전트 탭은 모두 사람용 화면이 아닌 프로그램용 연결로 CLI를 다룬다는 것이다. 에이전트 상태(initializing, running 등)와 권한 요청은 그 연결로 받은 이벤트로 정해진다(architecture.md).

provider마다 다른 연결 방식

provider 이름과 어댑터 클래스의 연결은 provider-registry.ts에 모여 있다. 어댑터마다 CLI와 이야기하는 방식이 다르다.

provider연결 방식근거
Claude CodeClaude Agent SDK의 query. SDK가 Claude Code 실행 파일을 자식 프로세스로 띄우고, Paseo는 그 프로세스를 띄우는 함수를 직접 넘긴다query.ts
Codexcodex app-server를 띄우고 표준 입출력으로 JSON-RPC 메시지를 한 줄씩 주고받는다codex-app-server-agent.ts
Copilot, CursorACP. 공개 SDK(@agentclientprotocol/sdk)의 연결 객체를 표준 입출력 위에 올린다acp-agent.ts
Pi, OMPpi --mode rpc처럼 RPC 모드로 띄우고 JSON 한 줄씩(JSONL) 주고받는다runtime.ts
OpenCodeopencode serve --port N으로 로컬 HTTP 서버를 띄우고 HTTP로 요청한다server-manager.ts

방식은 달라도 모두 CLI가 다른 프로그램과 연결하라고 따로 만든 모드를 쓴다. Codex의 app-server, Pi의 --mode rpc, OpenCode의 serve가 그런 모드이고, Claude Code에서는 SDK가 그 역할을 맡는다.

공통 인터페이스: AgentClient와 AgentSession

daemon은 provider 차이를 두 인터페이스로 가린다(agent-sdk-types.ts, 같은 파일).

  • AgentClient: provider 하나에 하나. 세션을 새로 만들고(createSession), 저장된 세션을 이어받고(resumeSession), 쓸 수 있는 모델과 모드 목록을 가져온다(fetchCatalog). CLI가 설치돼 있는지도 확인한다(isAvailable).
  • AgentSession: 대화 하나에 하나. 프롬프트를 보내고(startTurn), 이벤트를 구독하고(subscribe), 권한 요청에 답하고(respondToPermission), 멈추고(interrupt), 닫는다(close).

어댑터가 subscribe로 내보내는 이벤트도 공통 형식이다(agent-sdk-types.ts). 턴 시작과 끝(turn_started, turn_completed), 권한 요청과 해결(permission_requested, permission_resolved), 그리고 진행 기록 한 줄을 뜻하는 timeline이 있다. timeline 안의 항목은 사용자 메시지, 에이전트 답변, 생각 과정(reasoning), 도구 호출, 할 일 목록 같은 정해진 종류 중 하나다.

도구 호출도 종류별로 맞춘다. Claude의 Bash 도구와 Codex의 명령 실행은 이름이 다르지만, 어댑터를 지나면 둘 다 { type: "shell", command, cwd, output, exitCode } 모양이 된다(tool-call-detail-primitives.ts, codex-app-server-agent.ts). 앱이 provider와 상관없이 명령 실행을 같은 카드로 그릴 수 있는 이유다.

권한 요청이 휴대폰까지 갔다 오는 길

권한 요청을 중계하려면 먼저 에이전트를 기다리게 해야 한다. 에이전트는 답을 받을 때까지 다음 일을 하면 안 되고, 답은 몇 분 뒤 휴대폰에서 올 수도 있다. Paseo는 이것을 끝나지 않은 Promise로 해결한다.

Claude 쪽에서 보면 이렇다. SDK는 도구를 쓰기 전에 Paseo가 넘긴 canUseTool 콜백을 호출하고, 콜백이 돌려준 Promise가 끝나기를 기다린다. Paseo의 콜백은 요청을 공통 형식으로 만들어 permission_requested 이벤트로 내보낸 뒤, Promise의 resolve 함수를 pendingPermissions에 넣어 두고 돌아간다(claude/agent.ts). 이 resolve를 부르기 전까지 Claude는 그 도구를 쓰지 못한 채 멈춰 있다.

Codex도 구조가 같다. app-server가 보낸 승인 요청을 받는 처리 함수가 Promise를 돌려주고, 그 Promise가 끝나야 Codex에 응답 메시지가 나간다(codex-app-server-agent.ts, app-server-transport.ts).

전체 흐름은 이렇다.

  1. 어댑터가 permission_requested를 내보내고 Promise를 열어 둔다.
  2. AgentManager가 요청을 그 에이전트의 대기 목록에 넣고, 사용자의 확인이 필요하다는 신호를 클라이언트들에 보낸다(agent-manager.ts).
  3. 휴대폰에서 승인하면 agent_permission_response 메시지가 daemon으로 온다(session.ts).
  4. AgentManager.respondToPermission이 그 세션의 respondToPermission을 부르고, 어댑터가 넣어 둔 resolve를 호출한다(agent-manager.ts, claude/agent.ts).
  5. 멈춰 있던 CLI가 답을 받고 다음 일을 한다.

에이전트 CLI는 휴대폰의 존재를 모른다. 자기가 부른 함수가 아직 값을 돌려주지 않았을 뿐이다.

Paseo 도구를 에이전트에 넣어 주는 법

3편에서 본 create_agent, send_agent_prompt 같은 도구는 Paseo가 에이전트에 준 도구다. 에이전트 CLI는 원래 이 도구를 모르므로 Paseo가 실행 때 넣어 줘야 한다. 여러 CLI가 공통으로 받아들이는 도구 연결 방식이 MCP라서, Paseo는 daemon에 MCP 서버(/mcp/agents)를 열고 에이전트 설정에 그 주소를 끼워 넣는다.

넣는 시점은 에이전트를 실행하기 직전이다. AgentManager는 저장할 설정(storedConfig)에서 Paseo 내부 MCP 서버를 빼고, 실행할 설정(launchConfig)에만 다시 넣는다(agent-manager.ts). 넣는 항목은 paseo라는 이름의 HTTP MCP 서버이고, 주소 끝에 ?callerAgentId=<에이전트 ID>가 붙는다(runtime-mcp-config.ts). MCP 서버는 이 값으로 누가 부르는지 알고, provider별 설정에 따라 그 에이전트에 보여 줄 도구를 거른다(providers.md).

눈여겨볼 설계 선택

MCP는 대비책이다. Paseo 도구는 MCP 도구로 구현돼 있지 않다. 도구 목록은 따로 있고, MCP는 그 목록을 전하는 수단 중 하나다. 도구를 직접 등록받을 수 있는 provider는 supportsNativePaseoTools를 켜고 목록을 그대로 받는다. 이때 daemon은 실행 설정에서 MCP 서버를 빼서 같은 도구가 두 번 들어가지 않게 한다(providers.md, agent-manager.ts). 태그 기준으로 이 플래그를 켜는 내장 provider는 OMP와 OpenCode(bridge 사용 시)이고, Claude와 Codex는 MCP로 받는다.

인증은 provider에게 맡긴다. 설계 문서는 모든 provider가 인증을 스스로 처리하고 Paseo는 API 키를 관리하지 않는다고 적는다(architecture.md). Claude 어댑터도 Claude Code의 기본 system prompt와 사용자, 프로젝트, 로컬 설정을 그대로 불러온다(claude/agent.ts). 터미널에서 쓰던 로그인과 CLAUDE.md가 Paseo 안에서도 그대로 적용되는 이유다.

terminal profile과 agent profile은 이름만 비슷하다. terminal profile은 터미널에서 실행할 명령 하나(command, args)다(terminal-profile.ts). agent profile은 provider, 모델, 모드, 생각 옵션을 묶은 에이전트 실행 설정이다(agent-profile.ts). 둘 다 Claude Code를 고를 수 있지만, terminal profile로 열면 화면만 있는 터미널 탭이 되고, agent profile로 열면 이번 편에서 본 어댑터를 거치는 에이전트 탭이 된다. agent profile에 system prompt가 없는 이유도 코드 주석에 있다. system prompt는 에이전트를 만들 때만 정할 수 있다. 그래서 profile에 넣어 두면 새 에이전트에는 적용되지만, 실행 중인 에이전트에 적용할 때는 아무 표시 없이 무시된다.

새 용어

  • JSON-RPC: 프로그램끼리 JSON 메시지로 함수를 부르는 약속. 요청에는 id, 부를 이름(method), 인자(params)를 담고, 응답은 같은 id로 결과를 돌려준다. id가 있어서 요청 여러 개를 동시에 보내도 어느 응답이 어느 요청의 것인지 알 수 있다.
  • ACP(Agent Client Protocol): 에디터나 오케스트레이터 같은 클라이언트가 에이전트 CLI와 대화하는 방법을 정한 공개 규약. 세션 만들기, 프롬프트 보내기, 스트리밍, 권한 요청 같은 메시지 형식을 정해 두어서, 이 규약을 따르는 CLI라면 클라이언트 쪽 코드 하나로 붙일 수 있다.
  • MCP(Model Context Protocol): 에이전트에 외부 도구를 붙이는 공개 규약. 에이전트 설정에 MCP 서버 주소를 넣으면, 에이전트는 그 서버가 알려 주는 도구 목록을 자기 도구처럼 부를 수 있다.
더 깊이

Codex와는 한 줄에 메시지 하나로 이야기한다.

Paseo의 Codex 클라이언트는 요청을 보낼 때 { id, method, params }를 JSON으로 만들어 끝에 줄바꿈을 붙여 app-server의 표준 입력에 쓴다. 응답이 올 때까지 id별로 Promise를 보관해 두고, 표준 출력에서 한 줄을 읽으면 같은 id의 Promise를 끝낸다(app-server-transport.ts). 방향은 반대로도 흐른다. Codex가 item/commandExecution/requestApproval 같은 요청을 보내면 Paseo가 등록해 둔 처리 함수가 받고, 처리 함수가 끝난 뒤에야 같은 id로 응답을 쓴다. 양쪽 모두 요청을 보내고 답할 수 있으므로, 권한 요청처럼 에이전트가 먼저 묻는 흐름도 같은 형식으로 오간다. 줄바꿈은 LF만 경계로 본다. 코드 주석에 따르면 Codex JSON 안에는 다른 줄 구분 문자가 그대로 들어올 수 있어서다(app-server-transport.ts).

주입하는 MCP 서버에는 실행마다 바뀌는 토큰이 붙는다.

주입 항목에는 Authorization: Bearer <토큰> 헤더가 들어간다(runtime-mcp-config.ts). 이 토큰은 daemon이 시작할 때마다 randomUUID()로 새로 만들고, 로컬 에이전트 설정에만 넣으며 원격 클라이언트에는 보내지 않는다(bootstrap.ts). 그래서 저장된 설정에 MCP 서버를 남겨 두면 daemon을 다시 시작한 뒤에는 맞지 않는 토큰이 된다. 앞에서 본 “저장할 때 빼고 실행할 때 넣기”는 이 문제를 피하는 효과가 있다. 다만 코드 주석이 이 연결을 직접 말하지는 않으므로 이 부분은 추론이다.

주입은 기본으로 꺼져 있다. 설정을 읽는 config.ts가 daemon.mcp.injectIntoAgents가 없으면 false로 정하고(config.ts), 공개 문서의 기본값 표도 false다(mcp.md). bootstrap.ts에는 ?? true라는 대비값이 있지만(bootstrap.ts), 설정 파일을 읽는 경로에서는 값이 이미 false로 정해져 넘어오므로 이 대비값까지 가지 않는다.

새 provider는 플러그인으로 붙인다.

docs/providers.md는 새 provider를 플러그인 SDK로 추가하라고 안내하고, 이때 CLI 연결 방식과 세션 상태는 플러그인이 맡고 실행 파일 위치와 환경 변수는 daemon이 정한다고 적는다(providers.md). daemon은 플러그인 provider도 AgentClient와 AgentSession을 구현한 객체(PluginAgentClient, PluginAgentSession)로 감싸서 내장 provider처럼 다룬다(plugin-provider.ts, 같은 파일). 플러그인이 붙는 방식은 8편에서 다룬다.
