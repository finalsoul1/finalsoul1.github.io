에이전트를 믿게 만드는 환경2편, 최근 글 2026.10.29
  1. 01에이전트를 믿게 만드는 역피라미드

    에이전트가 틀렸을 때 물어야 할 것은 "어떻게 다시 지시할까"가 아니라 "이 수정을 어느 층에 남길까"다. 코드, 자동 검사, 하네스, 글, 사람 리뷰 순서로 따져 보면 같은 실수를 두 번 고치지 않게 된다.

    2026.10.23
  2. 02에이전트가 코드를 짜도 사람에게 남는 것

    에이전트가 코드를 짜도 장애가 나면 호출을 받고 고치는 쪽은 사람이다. 그 코드를 한 줄씩 다 이해할 수는 없어도 기초 지식, 넓은 시야, 깊이 파고드는 힘은 사람에게 있어야 한다. 에러 없이 조용히 망가지는 문제를 알아보고, 어디부터 살펴볼지 판단하며, 낯선 문제를 끝까지 추적할 수 있어야 역피라미드의 다섯 층도 설계할 수 있다.

    2026.10.29
Paseo로 보는 에이전트 오케스트레이터8편, 최근 글 2026.10.29
  1. 01daemon 하나와 클라이언트 여럿

    에이전트 오케스트레이터의 중심은 화면이 아니라 내 컴퓨터에서 계속 도는 프로세스 하나다. Paseo에서는 daemon이 에이전트, 터미널, 워크스페이스를 모두 맡고, 데스크톱 앱, 모바일 앱, CLI는 WebSocket으로 daemon에 붙어 상태를 보여 주고 명령을 전하는 클라이언트다.

    2026.10.29
  2. 02워크스페이스

    워크스페이스는 daemon 하나 위의 작업 디렉터리(cwd) 하나에 id를 붙인 단위이고, 에이전트 세션은 모두 어떤 워크스페이스에 속한다. 디렉터리를 따로 떼어야 하면 Paseo는 git worktree를 만들고, 이름은 임시로 붙였다가 나중에 다시 짓는다. 다 쓴 워크스페이스는 기록을 지우지 않고 보관 표시만 한 뒤 디렉터리만 정리한다.

    2026.10.29
  3. 03한 워크스페이스의 세션들이 나눠 갖는 것

    한 워크스페이스의 세션들은 디스크(파일과 git 작업 트리)와 워크스페이스에 붙은 도구(터미널, 스크립트, 브라우저 탭)를 공유한다. 대화 기록, provider 세션, 모델과 모드 설정은 세션마다 따로 있고, Paseo는 세션에게 옆 세션이 있다는 사실도 알려 주지 않는다. 한 세션의 맥락이 다른 세션으로 넘어가는 길은 누군가 명시적으로 보내는 네 가지 경로뿐이고, 그중 셋은 기본값에서 꺼져 있는 Paseo 도구 주입을 켜야 쓸 수 있다.

    2026.10.29
  4. 04서로 다른 에이전트를 하나처럼 다루기

    Paseo는 에이전트 CLI의 터미널 화면을 읽지 않는다. provider마다 그 CLI가 제공하는 구조화된 연결 방식(Claude Agent SDK, codex app-server의 JSON-RPC, ACP 등)으로 붙고, 그 차이를 AgentClient와 AgentSession이라는 공통 인터페이스 뒤에 숨긴다. 그래서 daemon과 앱은 어떤 에이전트든 같은 형식의 진행 기록과 같은 권한 요청으로 다룬다.

    2026.10.29
  5. 05터미널, 파일, diff를 여러 기기에 그리기

    Paseo는 화면 코드 하나(Expo)로 iOS, Android, 웹, 데스크톱을 만들고, 플랫폼마다 크게 다른 부분만 파일을 나눠 따로 구현한다. 터미널 해석과 diff 색칠은 daemon이 맡는다. 터미널의 현재 화면은 daemon이 따로 띄운 터미널 worker 프로세스 안의 터미널 에뮬레이터가 들고 있고, diff 색칠은 daemon이 파일 전체를 읽어 끝낸 뒤 토큰으로 보낸다. 클라이언트는 받은 것을 자기 화면에 그린다.

    2026.10.29
  6. 06끊겼다 붙어도 화면이 맞는 이유

    Paseo는 휴대폰 연결이 언제든 끊길 수 있다고 보고 설계했다. daemon은 에이전트 기록 한 줄마다 번호를 붙이고, 앱은 마지막으로 받은 번호를 기억해 두었다가 번호가 건너뛰면 빠진 구간만 다시 받는다. 연결 경로는 계속 재 보다가 확실히 빠를 때만 바꾸고, 출력은 묶어서 보내 메시지 수를 줄인다.

    2026.10.29
  7. 07relay를 믿지 않고 통신하는 법

    Paseo는 relay를 믿지 않는 중계자로 두고, 휴대폰과 daemon이 직접 암호화한다. 휴대폰은 QR로 받은 daemon 공개키로 핸드셰이크를 해서 상대가 그 daemon이 맞는지 확인하고, 그 뒤 메시지마다 순서 번호를 넣어 암호화한다(새 방식인 protected 모드 기준). 다만 이 핸드셰이크는 휴대폰이 누구인지는 확인하지 않는다. 그래서 비밀번호를 정하지 않으면 페어링 링크를 가진 사람은 누구나 소유자 권한으로 붙는다.

    2026.10.29
  8. 08플러그인 하나, 실행되는 곳 두 군데

    Paseo 플러그인은 격리 장치 없이 그대로 믿고 실행하는 코드다. daemon은 플러그인 디렉터리 하나에서 번들 두 개를 만든다. 서버 번들은 daemon이 띄운 자식 프로세스에서 실행하고, 클라이언트 번들은 연결된 모든 앱 안에서 eval로 실행한다. 플러그인은 정해진 자리(라이프사이클 훅, provider, 화면과 패널)로만 붙고, Paseo에 함께 들어 있는 일부 provider와 사용량 조회 기능도 같은 경로로 들어온다.

    2026.10.29
아이콘 구조 개선5편, 최근 글 2026.10.27
  1. 01아이콘 198개가 모든 화면에 실리던 이유

    아이콘을 이름 문자열로 꺼내 쓰는 객체 하나에 모아 두면, 번들러는 어떤 아이콘이 쓰이는지 알 수 없어서 198개를 전부 싣는다. 아이콘 하나를 모듈 하나로 나누고 사용처가 그 모듈을 직접 import하게 바꿔서 해결했다.

    2026.10.21
  2. 02생성기와 codemod로 사용처 880곳 옮기기

    아이콘 모듈은 생성기가 만들고 사용처는 codemod가 바꿨다. 두 도구가 SVG 파일명에서 같은 규칙으로 컴포넌트 이름을 만들게 해서 서로 어긋날 수 없게 했다.

    2026.10.21
  3. 03예상 밖 비용, 번들 검사가 놓친 회귀, 전환 결과

    전환 도중에는 작은 SVG가 화면별 청크에 복사돼 빌드가 조금 커졌고, 전환을 마치자 거의 모든 화면이 받던 아이콘 묶음 청크(Turbopack 기준 gzip 약 24KB)가 사라졌다. 옛 Icon을 다시 쓰지 못하게 하는 방법으로는 번들 검사 대신 import 금지 lint를 골랐다.

    2026.10.21
  4. 04디자인 파일을 아이콘의 원본으로 만들기

    디자이너가 내보낸 SVG를 개발자가 손으로 고쳐 넣던 과정을 바꿨다. 이제 디자인 파일의 한 페이지를 원본으로 삼아 스크립트가 아이콘을 가져온다. 사람 기억에만 있던 손질 규칙은 코드로 옮겼고, 스크립트가 판단할 수 없는 아이콘은 멈추지 않고 건너뛴 뒤 디자이너에게 확인할 목록으로 출력하게 했다.

    2026.10.21
  5. 05같은 아이콘을 쓰는 다른 앱들

    이 아이콘을 쓰는 곳은 웹 앱 하나가 아니었다. 모바일 앱과 또 다른 웹 앱에도 같은 아이콘이 들어간다. 세 곳에 같은 방식을 요구하지 않고, 각자 지금 아이콘을 가져갈 수 있는 방식을 골랐다. 웹은 Figma 동기화와 스킬로 처리하고, 모바일 앱은 다운로드 페이지와 앱 쪽 스킬을 쓰며, 다른 웹 앱은 아이콘 저장소 분리를 기다린다.

    2026.10.27

LLM에 보낸 질문이 답이 되기까지7편, 최근 글 2026.10.20
  1. 01LLM이 한 토큰씩 답을 만드는 방식

    LLM은 답을 통째로 만들지 않고, 다음에 올 토큰 하나를 고르는 일을 답이 끝났다는 신호(끝 신호)가 나올 때까지 반복한다.

    2026.10.20
  2. 02글자가 숫자가 되기까지

    문장은 토큰으로 쪼개지고, 토큰마다 번호가 붙고, 각 번호는 정해진 숫자 목록(벡터)으로 바뀐다.

    2026.10.20
  3. 03앞 문맥을 섞는 법

    토큰마다 앞 토큰들을 참고할 비율을 정해 섞는다. 이 일을 레이어마다 되풀이하면 마지막 토큰 자리의 벡터에 지금까지의 문맥이 담긴다.

    2026.10.20
  4. 04다음 토큰 고르기

    마지막 벡터로 어휘의 토큰마다 점수를 내고, 점수를 확률로 바꿔서 하나를 뽑는다.

    2026.10.20
  5. 05한 번 한 계산은 다시 하지 않기

    처음 한 번은 입력 전체를 계산하고(prefill), 그 뒤로는 새 토큰 하나만 계산한다(decode). 앞 토큰의 계산 결과는 KV 캐시에 저장해 재사용한다.

    2026.10.20
  6. 06실제 요청 하나를 끝까지 따라가기

    요청 하나는 접수와 대기를 거쳐 토큰으로 잘린다. 서버는 prefill로 첫 토큰을 고른 뒤 decode로 한 토큰씩 이어 간다. 고른 토큰은 그때그때 보내고, <EOS>가 나오면 멈춘 뒤 KV 캐시 메모리를 비운다.

    2026.10.20
  7. 07이어지는 질문 세 개

    대화가 이어지면 앱 서버는 대화 전체를 다시 보내고, LLM 서버는 앞부분이 같으면 그 부분의 계산을 재사용한다.

    2026.10.20
