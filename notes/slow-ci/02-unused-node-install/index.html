느린 CI의 병목을 추적하다 / 02-02
지난 편한 줄 결론쉽게 보기로그를 열어 보니그 Node를 쓰는 잡이 없었다지우기 전에 로컬에서 재현했다제거와 결과새 용어배운 것
NOTES / 02 / 2026.11.12

안 쓰는 Node를 54초씩 설치하고 있었다.

지난 편

1편에서는 빌드 잡마다 러너를 받기까지 1분 넘게 기다리고, 그 가운데 DOWNLOAD_SOURCE 54초는 소스를 받지 않는 러너인데도 걸린다는 것을 봤다.

한 줄 결론

DOWNLOAD_SOURCE 54초는 러너가 Node 22를 설치하는 시간이었다. 실제 빌드 잡은 저장소마다 .nvmrc에 적힌 Node 24를 따로 설치해 썼으므로, 이 Node 22는 빌드마다 설치만 되고 쓰이지 않았다. 공유 러너를 쓰는 세 저장소를 모두 확인하고 로컬에서 재현한 뒤 설정을 지우자, 이 단계가 54초에서 2초로 줄었다.

쉽게 보기

출장 갈 때마다 회사가 노트북을 한 대 챙겨 주는데, 직원은 늘 자기 노트북을 따로 가져가서 쓰는 상황과 비슷하다. 회사 노트북은 매번 챙기는 시간만 들고 가방에서 꺼내지 않는다. 문제는 회사 노트북을 빼도 되는지 확인하려면 출장 가는 사람 모두에게 물어봐야 한다는 점이었다.

로그를 열어 보니

54초 구간의 빌드 로그를 타임스탬프와 함께 보면 이렇다.

07:43:27  Running command n $NODE_22_VERSION   (Node 22 설치 시작)
07:44:18  installed : v22.23.4                 (설치 끝, 약 51초)

러너의 빌드 설정(buildspec)에 아래 선언이 있었다.

phases:
  install:
    runtime-versions:
      nodejs: 22

CodeBuild 표준 이미지는 runtime-versions 선언을 보고 해당 버전의 Node를 설치한다. 이 러너에서는 그 설치가 DOWNLOAD_SOURCE 단계 안에서 실행돼, 54초 가운데 약 51초를 차지했다. 나머지 약 3초는 같은 단계의 다른 준비 작업이다. 선언을 지운 뒤 이 단계가 2초로 줄어든 것과도 맞는다.

그 Node를 쓰는 잡이 없었다

이 러너는 GitLab CI 잡을 CodeBuild에서 실행해 주는 호스트이고, 실제 빌드 잡은 그 위에서 필요한 Node를 직접 설치한다.

flowchart TB
  img["표준 이미지<br/>(기본 Node 24)"] --> rt["buildspec:<br/>Node 22 설치<br/>(약 51초)"]
  rt --> job["빌드 잡:<br/>.nvmrc를 보고<br/>Node 24 설치"]
  job --> use["실제 빌드는<br/>Node 24로 실행"]
  rt -. 쓰이지 않음 .-> use
  • 세 저장소가 이 러너를 공유한다.
  • 세 저장소 모두 잡 안에서 .nvmrc에 적힌 Node 24를 패키지 저장소에서 받아 설치하고, 그 Node로 빌드한다.
  • 잡이 설치한 Node 24가 PATH에서 앞에 오므로, buildspec이 설치한 Node 22는 호출되지 않는다.

표준 이미지(amazonlinux-x86_64-standard:5.0)의 기본 Node도 이미 24다. 결국 buildspec 선언은 기본값 24를 22로 내리고, 잡은 그것을 다시 24로 올리고 있었다.

지우기 전에 로컬에서 재현했다

공유 러너라 설정을 잘못 바꾸면 세 저장소의 CI가 함께 멈춘다. 그래서 변경을 요청하기 전에 같은 표준 이미지를 로컬에서 받아 확인했다.

  • runtime-versions 없이 node -v를 실행하면 v24.22.2가 나왔다. 선언을 빼도 node 명령은 그대로 남는다.
  • 빌드 잡의 Node 설치 단계를 그대로 실행해 보니, 패키지 저장소에서 Node 24를 받아 설치하는 과정이 정상 동작했다.
  • Node 설치 전에 도는 준비 단계(도구 설치, 캐시 복원)는 Node를 쓰지 않았다. 기본 Node가 몇 버전이든 영향이 없다.

세 저장소 모두 자기 Node를 설치하고 이미지 기본값도 24이므로, 선언을 지워도 안전하다고 판단했다.

제거와 결과

근거를 정리해 인프라 담당에게 buildspec의 runtime-versions: nodejs: 22 제거를 요청했다. 적용 직후 같은 러너의 새 빌드를 측정했다.

구간제거 전제거 후
DOWNLOAD_SOURCE54초2초

빌드 하나당 약 52초가 줄었고, 이 러너를 쓰는 세 저장소에 모두 적용됐다. MR 하나가 빌드 잡 5~6개를 돌리므로 줄어든 시간은 빌드 수만큼 쌓인다. on-demand 러너는 빌드 시간만큼 비용을 내므로 비용도 같은 비율로 준다.

새 용어

  • buildspec: CodeBuild가 빌드할 때 실행할 단계와 명령을 적은 설정 파일.
  • runtime-versions: buildspec의 install 단계에서 표준 이미지에 설치할 언어 런타임 버전을 지정하는 항목.
  • .nvmrc: 저장소에서 쓸 Node 버전을 적어 두는 파일. nvm 같은 도구와 CI 스크립트가 이 값을 읽어 Node를 설치한다.
  • 표준 이미지: AWS가 제공하는 CodeBuild 기본 빌드 이미지. 여러 런타임이 미리 들어 있다.

배운 것

  • 설명되지 않는 숫자에서 출발한다. “소스를 받지 않는데 소스 단계가 54초”라는 어긋남이 실마리였다. 앞뒤가 맞지 않는 측정값은 원인을 찾을 때까지 넘기지 않는다.
  • 공유 자원을 바꾸기 전에 쓰는 쪽을 모두 확인한다. 러너 하나를 세 저장소가 쓰고 있었다. 한 저장소만 보고 지웠다면 나머지 두 저장소가 깨졌을 수 있다. 세 저장소의 CI 설정을 모두 열어 Node 22를 쓰는 잡이 없다는 것을 확인한 뒤에야 안전하다고 말할 수 있었다.
  • 되돌리기 어려운 변경은 미리 재현한다. 공유 러너가 깨지면 세 저장소의 CI가 함께 멈춘다. 같은 이미지로 로컬에서 먼저 실행해 본 덕분에, 변경 요청에 확인 결과를 근거로 붙일 수 있었다.
