같은 아이콘을 쓰는 다른 앱들.

지난 편

디자인 파일의 Icon Export 페이지를 원본으로 삼아 sync:icons가 아이콘을 가져오게 했다. 디자이너가 Slack으로 요청하면 에이전트 스킬이 동기화, MR, “반영 완료” 답글까지 같은 순서로 처리한다.

한 줄 결론

이 아이콘을 쓰는 곳은 웹 앱 하나가 아니었다. 모바일 앱과 또 다른 웹 앱에도 같은 아이콘이 들어간다. 세 곳에 같은 방식을 요구하지 않고, 각자 지금 아이콘을 가져갈 수 있는 방식을 골랐다. 웹은 Figma 동기화와 스킬로 처리하고, 모바일 앱은 다운로드 페이지와 앱 쪽 스킬을 쓰며, 다른 웹 앱은 아이콘 저장소 분리를 기다린다.

앱이 아이콘을 코드로 참조하지 않는 이유

가장 좋은 모습은 웹과 같다. 원본 SVG에서 앱 코드가 쓸 상수를 생성기로 만들고, 앱은 그 상수를 참조한다. 아이콘 이름이 바뀌면 컴파일 단계에서 바로 드러난다.

앱 쪽에 물어보니 바로 그렇게 하기는 어려웠다. 앱에도 에셋 상수 파일을 만드는 스크립트가 있지만, 그 파일의 일부는 손으로 관리되고 있었다. SVG 말고도 PNG와 애니메이션 파일의 상수가 같은 파일에 있고, 그중에는 손으로 붙인 이름과 일부 파일만 등록한 구간이 섞여 있었다. 앱의 SVG 폴더에는 디자인 파일에 없는 분류(커뮤니티, 이모지, 로고, 일러스트)도 있었다. 웹 쪽 생성기가 앱 코드까지 만들려면 이 정리가 먼저 끝나야 했다.

웹 쪽에도 사정이 있었다. 아이콘이 지금 디자인 시스템 패키지 안에 있는데, 마침 아이콘만 따로 떼어 내는 작업을 준비하고 있었다. 앱용 생성기를 지금 붙이면 분리할 때 위치와 배포 방식을 다시 바꿔야 한다. 그래서 앱 코드 생성은 아이콘 모듈을 분리한 뒤에 지원할 계획이고, 그 전까지는 다운로드 페이지를 제공하기로 했다.

앱 쪽이 다운로드 페이지를 자동화했다

4편에서 다운로드 페이지를 만들 때는 사람이 검색해서 아이콘 하나를 받는 장면을 생각했다. 그래서 검색을 다듬었고 zip 다운로드는 남겨 두기만 했다. 그런데 앱 쪽이 반영 작업을 자동화할 때 쓴 것은 zip이었다.

다운로드 페이지를 안내받은 앱 개발자는 이틀 뒤 앱 저장소에 아이콘 반영 스킬을 추가했다. 스킬은 이렇게 동작한다.

  1. 다운로드 페이지 HTML에서 zip 링크를 찾아 내려받는다. 페이지에 적힌 기준 브랜치, 날짜, 커밋도 함께 출력한다.
  2. 빈 작업 폴더에 압축을 풀고, SVG가 아닌 파일이나 폴더 밖을 가리키는 경로가 있으면 멈춘다.
  3. zip에 들어 있는 분류 폴더만 통째로 바꾸고, zip에 없는 분류는 그대로 둔다.
  4. 상수 파일을 다시 만들되 SVG 구간만 끼워 넣는다. 손으로 관리하는 구간은 건드리지 않는다.
  5. 사라진 상수를 쓰는 곳을 찾아 대체 후보를 보여 준다. 후보가 없는 아이콘은 고치지 않고 보고한다.
  6. 커밋 전에 사람의 확인을 받는다.

3번과 4번은 앞에서 말한, 아직 정리되지 않은 부분을 피해 가는 장치다. 5번은 스크립트가 판단할 수 없는 것을 사람에게 넘긴다는 점에서 4편의 동기화 스크립트와 같다.

스킬을 추가한 날, 앱 쪽은 최신 묶음을 반영하는 작업도 시작했다. 이때 알림 화면의 썸네일 아이콘 10종을 라이트 모드와 다크 모드용 아이콘으로 바꿨다. 그 전에는 앱이 단일 아이콘에 포인트 색을 덧입히고 있었고, 썸네일 위에 겹치는 작은 아이콘 배지는 다크 모드에서도 검은색으로 보였다. 디자인 파일에서 모드별 아이콘을 따로 제공하기 시작하면서 덧입히던 색 처리를 지우고 아이콘 원래 색을 그대로 쓰게 됐다.

이렇게 다운로드 페이지는 사람이 보는 화면이면서 앱 쪽 스크립트의 입력이 됐다. 앱 스킬은 페이지 구조가 바뀌면 멈추고 보고하게 돼 있다. 그래서 웹 쪽에서 이 페이지를 고칠 때는 zip 링크와 메타 정보처럼 앱 스킬이 읽는 부분을 함께 봐야 한다.

다른 웹 앱은 저장소 분리를 기다린다

1편에서 쓴 것처럼, 다른 웹 앱 하나는 이 DS 코드를 복사해 동기화하는 방식으로 쓴다. 이 앱은 공유 코드를 동기화로만 받고 직접 고치지 않으므로, 웹의 동기화 스크립트와 스킬을 그 저장소에서 돌릴 수 없다. 옛 Icon 사용처도 432곳 남아 있다(3편). 그래서 디자이너에게 새 요청 방식을 안내할 때, 이 앱에는 아직 같은 방식을 쓸 수 없다고 함께 적었다.

이 앱에도 같은 흐름을 열어 주려면 아이콘을 별도 저장소로 떼어 내야 한다. 어떻게 나눌지 정하려고 최근 6개월의 머지 기록으로 단위별 변경 빈도를 쟀다. 단위는 공통 코드(core), DS 컴포넌트(core-ds), 아이콘, 이렇게 셋이다.

단위주당 태그 수(MR마다 찍을 때, 최근 13주)변경이 있던 주
core + core-ds12.213주 모두
아이콘1.213주 중 7주

셋을 한 저장소에 두면 아이콘 하나를 반영할 때도 주 10회 넘게 나가는 공통 코드의 배포 흐름을 그대로 거쳐야 한다. 반대로 셋을 모두 나누면 DS가 공통 코드를 참조하는 56개 파일이 저장소 경계를 넘고, 앱마다 core와 core-ds 버전 조합이 맞는지 계속 관리해야 한다.

아이콘 쪽은 사정이 달랐다. 아이콘 컴포넌트가 DS에서 참조하는 것은 클래스 병합 함수 cn 하나뿐이었다. 이 참조를 끊으면 아이콘은 다른 단위를 참조하지 않는다. 그래서 core와 core-ds는 한 저장소에 두고 아이콘만 떼어 내는 안을 추천했다. 아이콘 변경은 대부분 추가라서 호환이 깨질 일이 적고, 삭제와 이름 변경만 deprecation을 거치면 된다. 분리 방식은 아직 결정되지 않았다.

각자 고른 방식

사용처지금 방식이 방식을 고른 이유다음 단계

처음에는 세 곳이 같은 방식을 쓰는 것이 목표처럼 보였다. 하지만 지금 같은 방식을 요구하면, 앱은 정리되지 않은 상수 파일부터 고쳐야 하고 다른 웹 앱은 동기화 구조부터 바꿔야 한다. 그래서 방식은 각자 정하게 두고 원본만 하나로 맞췄다. 세 곳 모두 디자인 파일의 같은 페이지에서 나와 웹 저장소에 머지된 아이콘을 받는다.

남은 일

  • 아이콘 저장소 분리 방식을 정한다. 추천안은 core + core-ds와 아이콘, 두 저장소로 나누는 것이다.
  • 분리한 뒤 앱 코드 생성을 지원하고, 다른 웹 앱에도 같은 흐름을 적용한다.
  • Icon과 iconMap 삭제는 다른 웹 앱의 전환을 기다린다.

돌아보며

다섯 편에 걸쳐 쓴 일을 한 문단으로 줄이면 이렇다. 번들러가 정적으로 판단할 수 있는 모양으로 구조를 바꾸고, 그 모양을 생성기와 codemod가 만들게 했고, 원본인 디자인 파일의 변경을 코드까지 반영하는 과정을 스크립트로 만들었다. 같은 아이콘을 쓰는 다른 앱에는 각자 지금 받을 수 있는 경로를 열어 뒀다.

이 과정에서 여러 번 확인한 것은 세 가지다.

  • 검증은 통과 여부보다 무엇을 비교했는지가 중요하다. 실패 목록이 같다는 이유로 “회귀 없음”이 나왔고, 캐시 조건이 달라 2,396개가 다르다고 나왔다.
  • 도구가 말해 주지 않는 동작은 직접 확인한다. codemod는 건너뛴 곳을 말하지 않았고, oxlint는 설정을 합치지 않았고, 번들 검사는 작은 회귀를 놓쳤다.
  • 판단이 필요한 것은 멈추지 말고 목록으로 넘긴다. 동기화 스크립트가 모르는 것을 보류하고 확인 요청 문구를 출력하게 바꾼 뒤에야, 디자이너와 개발자가 각자 할 일을 나눌 수 있었다. 앱 쪽 스킬도 대체 후보가 없는 아이콘을 고치지 않고 보고한다.
