지난 편한 줄 결론들어가며다 읽을 수도, 안 볼 수도 없다시스템을 책임진다는 것사람에게 필요한 세 가지역피라미드에 맞춰 보면아이콘 작업에서 겪은 두 가지정리: 에이전트와 일할 때 사람이 챙길 것출처

에이전트가 코드를 써도 사람에게 남는 것.

지난 편

1편에서는 에이전트의 실수를 바로잡는 방법을 코드, 자동 검사, 하네스, 글, 사람 리뷰의 다섯 층으로 나눴다. 맨 아래 사람 리뷰에는 스펙을 잘못 이해한 구현, 설계 선택, 범위 판단처럼 기계가 판정할 수 없는 문제만 남긴다.

한 줄 결론

에이전트가 코드를 써도 장애가 나면 호출을 받고 고치는 쪽은 사람이다. 그 코드를 한 줄씩 다 이해할 수는 없어도 기초 지식, 넓은 시야, 깊이 파고드는 힘은 사람에게 있어야 한다. 에러 없이 조용히 망가지는 문제를 알아보고, 어디부터 살펴볼지 판단하며, 낯선 문제를 끝까지 추적할 수 있어야 역피라미드의 다섯 층도 설계할 수 있다.

들어가며

1편에서는 위 네 층이 거르지 못한 문제만 사람이 마지막에 본다고 했다. 그런데 에이전트가 쓴 코드를 다 읽지 못한다면, 무엇을 알고 있어야 그런 문제를 리뷰에서 알아보고 장애가 났을 때 직접 고칠 수 있을까.

Adrian Quiroga는 블로그 글 “Here Be Monsters”에서 이 질문을 다뤘다. 그 글에서 제시한 세 가지 조건을 정리하고, 1편의 역피라미드와 실제 작업 경험에 맞춰 본다.

다 읽을 수도, 안 볼 수도 없다

에이전트가 쓴 코드를 대하는 태도는 흔히 두 극단으로 나뉜다.

  • 모든 줄을 이해해야 한다: 에이전트가 코드를 만드는 속도는 사람이 읽고 이해하는 속도보다 훨씬 빠르다. 신입이 몇 년씩 손으로만 코딩하며 배우게 둘 회사도 드물고, 에이전트가 만든 코드를 매번 끝까지 리뷰하는 방식이 업계 전반에 자리 잡기도 어렵다.
  • 구현은 보지 않아도 된다: 자동 검사만 통과하면 끝났다고 보는 입장인데, 검사를 통과하는 일과 코드가 안전한 일은 다르다.

“Here Be Monsters”에는 이런 사례가 나온다. CI에서 SonarQube가 App.tsx의 순환 복잡도(cyclomatic complexity) 경고를 띄웠다. 파일 전체는 30줄 남짓이었지만, 열어 보니 그중 15줄은 Codex가 줄마다 컴포넌트 하나씩을 통째로 한 줄에 몰아 쓴 코드였다. prettier로 줄바꿈을 펼쳐 봐도 분기 수가 줄어드는 것은 아니니 복잡도 경고는 그대로였다. 로직을 읽어 보니 예외 처리가 다소 과했을 뿐 틀린 곳은 없었고, 복잡도 역시 요구사항상 필요한 수준이었다. 그래서 Codex에게 SonarQube 검사를 통과하게 해 달라고 했더니, Codex는 코드를 파일 10개로 쪼갰다. CI는 통과했고 그대로 배포됐다. Quiroga는 새로 생긴 파일 10개를 한 번도 읽어 보지 않은 채 배포했다며, 자칫 훨씬 큰 사고로 이어질 수도 있었다고 적었다.

역피라미드에 대입해 보면 여기서 2층 자동 검사의 한계가 드러난다. 검사는 통과 기준만 정할 뿐이고, 에이전트는 그 기준을 통과하는 가장 짧은 길을 고른다. 이번에는 코드를 여러 파일로 쪼개는 편이 가장 짧았고, 그 결과 사람이 모르는 코드만 늘었다.

시스템을 책임진다는 것

Quiroga는 시스템을 소유한다는 말을 단순하게 정의한다. 장애가 났을 때 호출받는 사람이 곧 그 시스템의 주인이라는 뜻이다. 지금까지 엔지니어는 코드를 직접 짜고 장애를 겪으면서 시스템이 어떻게 돌아가는지 머릿속에 그림을 그렸다. 에이전트가 코드를 대신 쓰면 이 그림이 저절로 그려지지 않는다. 그래도 장애 알림은 여전히 사람에게 온다.

그래서 질문이 바뀐다. 모든 코드를 다 이해할 방법을 찾는 대신, 장애가 났을 때 문제를 고치려면 최소한 무엇을 알고 있어야 하는지 묻게 된다.

사람에게 필요한 세 가지

1. 기초 지식: 에러 없이 조용히 망가지는 문제를 알아본다

시스템이 겉으로는 돌아가는데 느려지거나 가끔 실패할 때가 가장 찾기 어렵다. 당장 에러가 나지 않으니 자동 검사도 그대로 통과한다. 이런 징후를 알아보려면 자료구조, 알고리즘, 네트워크, 동시성, 분산 시스템 같은 기초 지식이 필요하다.

예를 들어 잠수 로봇이 2m 내려가는 데 4초, 4m에 16초, 16m에 256초가 걸린다고 하자. 깊이가 두 배가 될 때 시간이 네 배로 늘어난다면 O(n^2) 복잡도를 의심해야 한다. 세부 구현을 다 몰라도 그런 복잡도가 있다는 사실만 알면 이상하다는 점을 알아차릴 수 있다.

2. 넓은 시야: 어디부터 살펴볼지 안다

모든 분야의 전문가가 될 필요는 없다. 시스템이 이상할 때 무엇부터 찾아봐야 할지 알면 된다. 이런 시야를 한 번에 길러 주는 수업은 없으므로, 평소 꾸준히 읽고 궁금해하며 새로 접한 사례를 자기 업무와 연결해 보면서 조금씩 넓혀 가야 한다.

3. 깊이 파고드는 힘: 필요할 때 낯선 문제를 끝까지 판다

평소에는 개념만 알아 두더라도, 문제가 생기면 낯선 영역에 직접 뛰어들어 필요한 지식을 그 자리에서 익히고 원인을 밝혀내야 한다. Quiroga가 에이전트로 만든 오케스트레이터에서는 안정성 문제와 생명주기 버그가 계속 터졌다. 에이전트에게 여러 번 수정을 맡겼지만 해결되지 않자, 예전에 Kubernetes 책에서 읽은 “레벨 트리거 상태 머신”이라는 말을 떠올렸다. 그 개념을 찾아 공부한 뒤 핵심 구조를 다시 설계했고, 그 뒤로 시스템은 안정적으로 돌아간다고 한다.

예전에 읽어 둔 개념 덕분에 어디를 찾아볼지 알았고(넓은 시야), 실제 설계에 적용할 수 있을 만큼 파고들었다(깊이). 혼자 풀기 어려운 문제라면 도움을 구하는 일도 문제를 끝까지 해결하는 과정에 들어간다.

역피라미드에 맞춰 보면

이 세 가지는 5층 사람 리뷰에서만 쓰이지 않는다. 역피라미드의 위쪽 층을 설계할 때도 그대로 바탕이 된다.

사람에게 필요한 것연결되는 층환경에 남기는 방법
기초 지식2층 자동 검사에러 없이 느려지거나 실패하는 문제를 발견하면, 성능 테스트나 복잡도 검사를 추가해 다음부터 기계가 거르게 한다
넓은 시야4층 글시스템 경계와 입출력, 요청 흐름을 시퀀스 다이어그램 같은 지도로 남겨, 내부 구현을 다 몰라도 장애 지점을 따라갈 수 있게 한다
깊이 파고드는 힘1층 코드베이스오케스트레이터 사례처럼 같은 버그가 반복되면, 증상만 고치는 대신 그 버그가 생길 수 없는 구조로 코드를 바꾼다

5층 리뷰에서 사람이 직접 챙겨야 할 대상도 더 분명해진다. “Here Be Monsters”를 다룬 Hacker News 토론에서는 댓글 작성자 다섯 명가량이 데이터 스키마, 저장 형식, 통신 프로토콜, 공개 API만큼은 사람이 직접 설계하거나 검토한다고 적었다. Quiroga 역시 에이전트가 어떻게 짜 오든 스키마만큼은 늘 직접 확인한다고 답했다. 스키마와 인터페이스는 한번 정하면 뒤따르는 구현이 모두 여기에 맞춰지므로 나중에 바꾸기 어렵다. 에이전트가 잘못 짠 함수 하나는 다시 짜면 그만이지만, 잘못 정한 스키마를 고치려면 그 위에 쌓인 코드와 데이터를 전부 옮겨야 한다.

아이콘 작업에서 겪은 두 가지

아이콘 구조 개선 작업에서도 자동 검사만 믿었다면 놓쳤을 순간이 두 번 있었다. 둘 다 검사는 문제가 없다고 나왔지만 실제로는 문제가 있었다.

“회귀 없음”이라는 보고. 기존 아이콘을 개별 컴포넌트로 교체한 뒤, 에이전트는 시각 회귀 테스트 결과를 근거로 회귀가 없다고 보고했다. UI 비교를 어떻게 했는지 되물었더니 전혀 다른 상황이 드러났다. 시각 회귀 테스트 46개는 코드를 바꾸기 전과 후 모두 같은 이유로 실패하고 있었다. 스토리 id가 맞지 않아 픽셀을 비교하기도 전에 멈췄고, 기준이 될 스냅샷 이미지도 저장소에 없었다. 에이전트는 실패 목록이 전후로 같다는 결과를 두고 회귀가 없다고 해석해 보고한 것이었다. 비교 방법을 되물을 수 있었던 것은 시각 회귀 테스트가 원래 무엇과 무엇을 비교하는지 알고 있었기 때문이다. 앞선 SonarQube 사례와 마찬가지로, 통과 여부보다 검사가 실제로 무엇을 확인했는지를 따져 봐야 했다.

임계값을 빠져나간 회귀. 아이콘 198개를 한데 묶어 두던 옛 Icon 컴포넌트를 누군가 다시 쓰면, 198개가 전부 번들에 다시 실린다. 이를 막으려고 청크 하나에 SVG가 100개를 넘으면 CI를 실패시키는 번들 검사를 구상했다. CI에 넣기 전에 파일 하나만 옛 Icon으로 되돌려 시험해 보니, 가장 큰 청크에 들어간 SVG는 93개에 그쳐 검사를 그냥 통과했다. 사용처가 한 곳뿐이면 아이콘 묶음이 공유 청크 하나에 모이지 않고, 그 라우트의 청크 여러 개로 쪼개져 들어가기 때문이다. 번들러가 청크를 어떻게 나누는지 몰랐다면 그대로 지나쳤을 허점이었다. 그래서 빌드 결과를 세는 대신 lint 규칙으로 옛 Icon import 자체를 막았다. 기초 지식으로 검사의 허점을 찾아내고, 더 확실한 2층 자동 검사로 바꾼 사례다.

정리: 에이전트와 일할 때 사람이 챙길 것

  1. 검사를 어떻게 통과했는가. 코드를 억지로 쪼개거나 우회해서 통과했다면 결과를 직접 열어 본다.
  2. 에러 없이 느려지거나 가끔 실패하는 곳이 있는가. 기초 지식으로 원인을 추적하고, 재발을 막을 자동 검사를 추가한다.
  3. 장애가 났을 때 따라갈 지도가 있는가. 시스템 경계와 입출력, 요청 흐름을 글로 남긴다.
  4. 되돌리기 어려운 결정인가. 데이터 스키마, 저장 형식, 통신 프로토콜, 공개 API는 사람이 직접 설계하거나 검토한다.
  5. 같은 버그가 반복되는가. 에이전트에게 재시도만 시키지 말고 직접 파고들어 구조부터 고친다.

에이전트가 코드를 써도 장애가 나면 수습하는 몫은 사람에게 남는다. 그때 필요한 것은 모든 줄을 다 아는 것이 아니라, 이상한 징후를 알아보고 어디부터 살펴볼지 판단해 필요한 만큼 깊이 파고드는 힘이다. 역피라미드의 다섯 층을 계속 고쳐 나가는 일도 여기서 출발한다.
